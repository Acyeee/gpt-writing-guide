# GPT/Codex 文稿写作与修改经验

GPT、Codex 写的文稿有一些共同倾向：防御性强，措辞保守，喜欢交代自己，形式堆砌。下面的经验分两段使用：写作前用来约束模型，写完后用来检查和修改。这里只给方向，各领域的文体和格式按自己领域的规范处理。

规则冲突时的优先级：当前任务的明确要求 → 单位、项目或期刊的专门规范 → 本经验。

---

## 一、写作前

### （一）GPT 文稿的总体倾向

| 倾向 | 表现 | 修改方向 |
|---|---|---|
| 自我保护 | 处处留后路：“仍需进一步验证”“仅供参考”“视实际情况而定” | 直接陈述；确有限定的，集中交代一次 |
| 保守 | 不给结论，把判断推给任务书、上级或后续工作 | 给出已知的范围、常用值和建议 |
| 爱交代 | 介绍文件自己、介绍工作过程 | 只写内容和结果 |
| 求全 | 表格、清单、并列项堆满，同一内容多处出现 | 只保留必要的形式，同一内容只写一处 |
| 腔调 | 套话、直译腔、自造词、路标词 | 用规范书面语，读者一次能读懂 |

### （二）写作约束

让 GPT 或 Codex 写文件前，把下面九条交给它。Codex 可写入全局 AGENTS.md，网页版可粘贴在指令开头。

1. 动笔前先确认文件类型、读者、作者角色和依据材料；不清楚的先问。
2. 直接陈述结论、范围和建议。不写分散的免责句，不把结论推给任务书或后续工作；确有限定条件的，集中交代一次。
3. 成品只写内容和结果：不写“本节将”“本文件”式的自我交代，不写工作过程、版本、工具名和内部统计，过程写进日志。
4. 用规范书面语：不用“赋能、抓手、底座、闭环”等套话，不用直译腔和自造简称，缩写首次出现时加解释。
5. 不用“不是A而是B”、段尾升华、口号和设问；一句并列不超过三项；不用斜杠和符号代替文字。
6. 版式用黑白：表头加粗，不加底色；表格只放参数和对比；不加提示框和术语表。
7. 不新增原材料中没有的事实和数据，缺的列出来问；“没有”“不能”这类判断要有直接依据；“待核实”只用于确实拿不准的地方，并写明原因。
8. 只写要求的内容，不自行增加章节或字段；修改已有文件时先列问题清单，确认后最小原位修改。
9. 汇报时说清完成了什么、没完成什么、验证了什么。

### （三）指令模板

把方括号内的内容换成自己的。

**写新文件：**

> 请撰写【文件名称】。这是一份面向【读者】的【文件类型】，作者角色是【提供依据/制定规范/说明做法】，依据材料见附件。
> 按附件《GPT/Codex 文稿写作与修改经验》第一部分的九条写作约束执行。
> 动笔前先给出提纲和你对任务的理解，确认后再写；写完按第五部分自查清单检查后再交付。

**修改已有文件：**

> 请修改附件文稿。这是一份面向【读者】的【文件类型】，作者角色是【提供依据/制定规范/说明做法】。
> 先不要改文件，按附件《GPT/Codex 文稿写作与修改经验》第二部分列出问题清单（位置｜原文｜问题类型｜建议改法），逻辑和事实问题单独列出。
> 要求：不写免责句和推给后续的表述，不写工作过程，不新增原文没有的事实和数据，不调整已有结构。

分阶段的任务，要求每个阶段结束后停下来，交人审查后再继续。

## 二、八类常见问题

第1、2、7类最能体现 GPT 的特点，建议优先检查。

### 1. 防御性表述

| 表现 | 示例 | 改法 |
|---|---|---|
| 分散的免责句 | 各节末尾都写“以上结论仍需进一步验证” | 删除；待解决的问题集中在一处交代 |
| 把依据推给上级 | “根据任务要求，本方案需要……” | 直接陈述内容 |
| 把结论推给后续 | “具体参数视实际情况确定”“由后续论证决定”“可作为下一步工作的基础” | 给出已知的范围、常用值和建议 |
| 用“需复核”带过分歧 | 两份材料说法不同，只写一句“需进一步核实” | 把各方的说法和依据并列写出 |
| 同一限定逐条重复 | 每一条后都挂“（在条件允许时）” | 在总则或适用范围中交代一次 |
| 文件自我免责 | “本文件仅为通用模板，不替代……” | 删除；确有必要的写成适用范围条款 |

数值本身的条件（“约”“在……条件下”）和有实际约束的“通常”“可能”应当保留。去掉防御性表述，不等于把不确定的内容写成确定的。

### 2. 自我指涉与元话语

- 交代结构：“本节将从三个方面展开”“下表总结了……”“如前所述”。
- 交代文件做什么、不做什么：“本文件不另附表格”“无须在此签字”。
- 说明框、“重要提示”框。

改法：删除，直接进入内容。简短的交叉引用（“见附录A”）可以保留。

### 3. 过程性语言与内部信息

- 工作过程：“经过多轮讨论”“目前正在整合”。
- 版本和状态：“已完成第一版”。
- 内部统计和工具：收集了多少份材料、筛掉多少份，用了什么工具批量处理。

改法：只写“通过什么方法、得到什么结果”。过程写进工作日志，不写进成品。技术说明中的脚本、日志属于正文，不在此列。

### 4. 形式堆砌

- 什么都做成表格。
- 斜杠并列（“停机/报警”），改为顿号、“和”或“或”。
- 符号代替文字（“A＞B＞C”），写成完整句子。
- 一句话里并列五六项，一般控制在三项以内，更多的改表格或拆句。
- 文末口号、加粗提示、附加术语表。
- 版面装饰：表头深蓝底白字，彩色标题，红色警示字，灰色说明字，带底色的提示框。正式文件一般用黑白，表头加粗即可；需要强调的内容写进正文，不靠颜色区分。单位有统一模板的，按模板处理。

### 5. AI 腔、直译腔与自造词

判断标准：非本专业的读者能否一次读懂。

- **套话**：赋能、抓手、底座、打造、闭环、深度融合、全方位、本质上、真正的。
- **直译腔**：英文术语或句式直接搬过来，读者要反推原文才能理解。
- **自造词**：写作中临时起的简称，作者自己熟悉，读者并不知道。
- **口语词**：搞、弄、看看、试一下、复盘。
- **未解释的缩写**。

注意：
- 这些只是提示，不是禁词表。在上下文中自然、准确的词照常使用。
- “朴实”指不堆砌、不渲染，不等于口语化。正式文稿用规范书面语。

### 6. 句式模板

- “不是A，而是B”连续使用。
- 路标词堆叠：值得注意的是、换句话说、由此可见、总之。
- 段尾升华：“……为后续工作提供了重要支撑”。
- 多段使用同一句式开头。
- 设问、考试式提问，口号式收尾。

### 7. 口吻与主语错位

- **以“调研”“材料”作主语转述**：“调研进一步把问题分为……”。文件本身就是陈述主体，直接写“该问题可分为……”。
- **越位给别人定规矩**：论证材料写“验收时必须……”，应改为“建设时需重点考虑……”。
- **第一人称辩护**：“我们认为”“本报告坚持”。
- **换词不换口吻**：只把一个说法换成近义词，转述的姿态没变。要改句子结构。

### 8. 结构重复

- 同一内容多处出现，合并到最合适的一处。
- 各分节重复同样的公共内容。公共内容集中写一次，各节只写本节特有的内容。
- 后一章又把前一章的结论做一遍，先明确各章分工。
- 报告各章结构相似属于正常体例，不必为求变化打乱结构。

## 三、GPT/Codex 执行任务时的问题

让 GPT 或 Codex 修改文件、迭代指令、整理资料时，常见以下问题。

| 问题 | 表现 | 应对 |
|---|---|---|
| 范围扩张 | 每轮都加字段、加规则、加配置，文件越写越长 | 先定核心清单，新增内容须说明用途 |
| 只改不验 | 反复修改指令或文稿，没有标准答案对照，无法判断是否变好 | 先人工核对一小批作为标准，之后每次修改只针对已确认的问题 |
| 悄悄改条件 | 换了模型、参数或数据，没有说明，前后结果无法比较 | 要求记录每次运行的条件，改动写进日志 |
| 用“待核实”兜底 | “待人工判断”“需进一步确认”成了默认选项，到处出现 | 只有确实拿不准才标，并写明卡在哪里、依据是什么；常规缺失直接省略 |
| 编造补全 | 缺少的数值、编号、批准人等信息自行补上 | 明确要求不新增事实，缺的列出来交给人决定 |
| 改动越界 | 顺手重写没有问题的段落，调整已确认的结构 | 要求最小原位修改，结构调整先请示 |
| 复述走样 | 总结或“记住”一份规范时丢掉核心条目、读错原文，加入与规范冲突的建议 | 让它复述后逐条核对；重要任务直接附原文件，以原文件为准 |
| 汇报含糊 | “基本完成”“理论上可行”“建议进一步……”；或者反过来，只想了解进度，却得到长篇说明 | 要求说清完成了什么、没完成什么、验证了什么；详略按用途定，进度汇报一项一行 |

## 四、修改流程

按修改对象分两种情况：

- **单段文字**：直接修改，保留原意和合理结构，简要说明主要改动。
- **完整文件**：按下面的步骤，先诊断，确认后再改。

无法判断时，按完整文件处理。

1. **定位**：文件类型、读者、作者角色、已有材料。
2. **诊断**：通读全文，列出问题清单，分三层标注：
   - 表述层：第二部分的八类问题，给出具体改法；
   - 逻辑层：论点、证据和结论是否衔接；
   - 事实层：数据、引用和技术判断是否有依据。

   GPT 文稿在逻辑和事实层常见的疏漏：
   - 推断过头：资料里少见，就写成“没有”“不能”；
   - 前后不一致：多轮修改后，同一数字、同一判断在不同位置说法不同，或统计口径前后不同；
   - 越出职责：替别人下结论，引用自己没有的数据，把不归自己负责的事列为后续工作。

   逻辑和事实问题先列出，由作者决定怎么改。语言通顺不代表内容正确。
3. **最小原位修改**：只改有问题的句子，没有问题的段落不重写。
4. **慎用批量替换**：替换前逐处看上下文，替换后再搜索一遍，检查是否误改了包含该词的其他词语。
5. **不新增事实和数据**：缺少的列出来问作者，没有的标“待核实”。
6. **审阅意见要看用意**：审阅人的删改多针对表述风格，不等于认可或否定内容本身。
7. **交付**：重要文件先出审阅版（标出改动）和修改说明，定稿后再出干净版。

## 五、改后自查清单

- [ ] 有无新增的免责句、“仍需验证”、推给后续的收尾？
- [ ] 有无“本节将”“下表总结了”式的自我交代？
- [ ] 有无工作过程、版本状态、工具名、内部统计？
- [ ] 有无斜杠并列、超过三项的并列、用符号代替文字？
- [ ] 有无彩色表头、彩色字、带底色的提示框？
- [ ] 有无套话、直译腔、自造词？缩写首次出现是否有解释？
- [ ] 有无段尾升华、路标词堆叠、口号、设问？
- [ ] 主语是否为陈述对象本身？口吻是否与作者角色一致？
- [ ] 同一内容是否只出现在一处？多处出现的数字、判断和口径是否一致？
- [ ] “没有”“不能”这类判断是否有直接依据？
- [ ] 有无新增事实？“待核实”是否只用在确实拿不准的地方？
- [ ] 逻辑和事实问题是否已列给作者，没有擅自改写？

## 六、用于科研论文时

本经验主要来自报告、规程等论证类文稿。用于论文时，以下几条要调整：

- **措辞与证据强度相称**：第二部分要删的是分散、空泛的免责句。论文中的限定语要保留：有数据直接支持的写“表明”“说明”，推断写“可能”“提示”；局限性在讨论部分集中写，不能删去。
- **结构交代和第一人称**：引言末尾交代全文安排、英文论文用 we，都是正常体例，不按自我指涉处理。正文中反复出现的“如前所述”“下文将”仍要删。
- **方法写清过程**：方法部分的步骤、条件、软件和版本属于正文，要写到他人能够重复。“不写工作过程”只针对讨论和结论中对工作经历的叙述。
- **版式和修改方式**：按期刊模板，“一句并列不超过三项”“表头不加底色”不必套用。返修时用修订模式，并逐条回复审稿意见。

另需重点检查：

- **文献真实性**：GPT 会编造作者、题目、期刊和 DOI，也会把结论安到不相关的文献上。每条引用都要核对原文，确认文献存在，且确实支持所引内容。
- **夸大创新和效果**：“首次”“显著”“突破性”须有依据；“显著”只在有统计检验时使用。
- **结果与解释分开**：先写观察到什么，再写如何解释，不把推测写成结果。
- **英文文稿**：第二部分的中文套话表不适用。英文 GPT 文稿常见 delve、pivotal、crucial、“It is worth noting that”“plays a vital role”，以及过多的破折号和三项并列，检查思路相同。
